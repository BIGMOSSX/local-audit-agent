## 已验证（命令已运行，输出已阅读）

- `pnpm --filter @audit/auditd test`：364 通过、1 跳过。探测的 19 个用例用真实的回环 HTTP 服务端：正常列表、HTML/404/坏 JSON/空列表/顶层数组、超过 1 MB 的响应、无响应、发完响应头后卡住、302 不跟随、模型数量上限 200、坏 id（空、过长、控制字符、双向控制字符、零宽字符、非字符串）与重复 id、默认候选端口表有效。
- 环境代理用例：子进程里设置 `NODE_USE_ENV_PROXY=1` 与 `HTTP_PROXY` 指向一个回环“代理”，探测仍直连目标，代理收到 0 个请求。此用例在改用 `node:http` 之前是红的（探测拿到了代理伪造的列表）。
- `pnpm --filter @audit/desktop test`：91 通过（客户端解析、设置页的检测/无结果/失败/重新检测/并发点击/离开页面后的迟到结果、首页状态行、文案规则）。
- `models.list` 的 handler：空参数通过，非空参数在探测前被 `invalid_params` 拒绝。
- Rust 侧无需改动：`allowlist.rs` 已含 `models.list`，`sidecar.rs` 已有 30 秒超时；探测最坏约 0.8 秒。

## 独立验收

fable 5.1 复核（结论：采纳并修改）。已按测试先行修复：环境代理会把探测引出回环（高）；上限用例里坏 id 断言形同虚设（中）；一个用例会访问开发机的真实端口（中）；文案把尚未上线的“基础检查”说成已存在（中）；双向控制/零宽字符未过滤（低）；计划里“无请求头”的说法不准确（低）。

## 未验证

- 这台机器没有真实的本机模型服务，没有对真实服务做过检测；候选端口（1234、8000、8080、11434）是规格要求“待核实”的常见默认值，未对照实际软件核实。
- 真实窗口里的设置页版式；macOS / Windows 上的实际表现。
- StrictMode 下的双重挂载只做了代码推理，没有运行验证。
- 离开设置页再进入时可能有两次探测短暂重叠（各不超过 0.8 秒，旧结果被丢弃），未处理。

## 安全评审

1. 只访问 `127.0.0.1`，不扫描局域网；探测是不带正文、不带凭据的 GET，不跟随重定向；使用显式 `Agent`，环境代理无法截走。
2. 探测结果不落盘、不记录日志、不上传；所有错误在探测内吞掉，不会进入服务端日志。
3. 响应体上限 1 MB，模型数上限 200，单个 id 上限 200 字符；id 作为纯文本渲染。
4. 找到的模型“不会被使用”：能力探测和质量门槛尚未开发，界面也不提供“使用”按钮，没有在线/离线卡片。
5. 无新的 IPC 方法，无新的 webview 权限。
